# Инструкция по запуску фаззинг-тестов и анализу покрытия кода

Этот документ описывает полный цикл работы: автоматизированный запуск фаззинг-тестов в репозиториях `corax` и `kafka-fork`, сбор трейсов выполнения и последующий анализ покрытия кода.

## Структура окружения

Скрипты ожидают, что репозитории расположены в одной корневой папке:
```text
sources/
└── corax/
    ├── corax/                       # Основной репозиторий проекта
    ├── kafka-fork/                  # Форк Кафки с подтянутыми модулями
    └── tracing-agent-c/             # Текущий репозиторий с агентом и утилитами
```

---

## Шаг 1. Запуск фаззинг-тестов и сбор трейсов

Скрипт запуска автоматически переходит в корень репозитория `corax`, выполняет очистку и запускает **140 фаззинг-тестов**, найденных по аннотации `@FuzzTest`.

Для запуска перейдите в директорию анализатора и выполните:
```bash
cd tracing-analyzer
./run-tests.sh
```

### Важные особенности запуска:
- Скрипт принудительно прокидывает версию Scala `-PscalaVersion=2.13`.
- Используется флаг `--rerun-tasks` для гарантированного сброса кэша Gradle.
- Для тестовых JVM передаются критичные флаги отключения инлайнинга: `-XX:-Inline -Xmixed`.
- **Результат:** Сырые логи трассировки выполнения складываются в общую папку: `corax/corax/tracing/` (файлы `.out`).

---

## Шаг 2. Анализ покрытия кода и сбор отчетов

После завершения тестов необходимо обработать сырые логи `.out`, чтобы понять, какие методы были реально вызваны.

### 2.1 Актуализация эталонного списка JAR
Перед генерацией отчетов необходимо обновить входной перечень зарегистрированных библиотек, иначе отчет по новым зависимостям будет некорректным.
1. Перейдите на внутреннюю страницу базы знаний проекта:  
   👉 [https://portal.works.prod.sbt/swtr/wiki/unit/KFK-448](https://portal.works.prod.sbt/swtr/wiki/unit/KFK-448)
2. Скопируйте оттуда актуальный список официально одобренных JAR-файлов релиза.
3. Вставьте его в локальный файл `tracing-analyzer/registered-jars.txt`, полностью заменив старое содержимое.

### 2.2 Генерация маппинга классов и JAR-файлов
Строим карту соответствия скомпилированных классов и JAR-пакетов системы:
```bash
./generate-mapping.sh
```
*Результат работы:* файл `reports/class_jar_mapping.csv`.

### 2.3 Анализ трейсов и генерация финального отчета
Запустите основной анализатор, который сопоставит сырые логи фаззинга с полученным маппингом классов и отфильтрует новые JAR по обновленному на шаге 2.1 эталону:
```bash
./analyze-traces.sh
```

### Какие отчеты появятся в папке `reports/`:
- `matched_methods.csv` — **Главный отчет**. Список конкретных сигнатур методов бизнес-логики (в формате JVM-дескрипторов) с указанием JAR-файла, в котором они исполнились.
- `matched_jars.txt` — Список всех JAR-файлов (компонентов системы), код внутри которых был затронут в процессе фаззинга.
- `new-jars.txt` — **Дельта-отчет**. Список новых/незарегистрированных JAR-файлов, которые были обнаружены при прогоне, но еще отсутствуют в эталонном перечне `registered-jars.txt` (сигнал для обновления документации на портале).
